# تشغيل مكتب الرئيس التنفيذي على Cloudflare Workers

## البنية

- الواجهة الحالية: React/Vite، تخدمها Workers Static Assets.
- الخادم: Express عبر `cloudflare:node` و`httpServerHandler`، مع `nodejs_compat`.
- D1 (`DB`): الحسابات المشفرة، اعتماد المستخدمين، الصلاحيات، سجلات الجهات، مؤشرات الأداء، التكليفات، التقارير وسجل التدقيق.
- R2 (`BUCKET`): مرفقات خاصة؛ لا تفعّل Public Development URL أو public custom domain على الحاوية. التنزيل يمر عبر API يتحقق من الحساب ونطاقه وملكية التقرير.
- لا تعتمد نسخة Workers على `fs` أو `EXECUTIVE_DATA_DIR`. يستمر مسار Node/Render السابق بالعمل مستقلًا.
- لا تضاف حسابات أو بيانات تشغيل تجريبية إلى القاعدة عند التهيئة.

كل طلب يحمل لقطة مستقلة من السجلات. تُحفظ التغييرات فقط ضمن دفعة D1 ذرّية مع رقم مراجعة؛ عند تعارض الحفظ تُلغى الدفعة وتعود 409، ولا تُكتب بيانات فوق تحديث مستخدم آخر. اعتماد الحساب وصلاحياته وسجل التدقيق يُحفظون معًا. تُرفع المرفقات إلى R2 قبل تثبيت مراجعها في D1، ويجري تنظيف المرفقات الجديدة عند فشل الحفظ. تعطل العملية بالكامل أثناء الرفع قد يترك ملفًا يتيمًا خاصًا دون مرجع، لكنه لا ينشئ تقريرًا بمرفق مفقود.

حدود التسجيل والدخول محفوظة في D1 لتستمر عبر العُقد وإعادة النشر. كلمات مرور المستخدمين تستخدم scrypt مع ملح عشوائي، والجلسات موقعة، وملف تعريف الارتباط HttpOnly/Secure/SameSite=Strict. يُرفض مصدر POST الخارجي. مفاتيح الخدمات لا تصل إلى الواجهة.

## التحقق المحلي

```bash
npm ci
cp .dev.vars.example .dev.vars
# أدخل بيانات مشرف اختبار محلي وسر جلسة محلي فقط في .dev.vars.
npm run check:workers
npm run test:workers
npm run db:migrate:local
npm run dev:workers
```

الاختبارات تستخدم D1 وR2 المحليين عبر Miniflare (محرك Workers)، وتتحقق من اعتماد المستخدم، وعزل التقارير والمرفقات، والتعليق، واستمرار البيانات وحدود المحاولات بعد إعادة التشغيل، ورفض تعارض الحفظ وتنظيف ملف R2 عند فشله.

## تهيئة الحساب لأول مرة

نفّذ على جهاز موثوق بعد تسجيل الدخول إلى حساب Cloudflare الذي سيملك المنصة:

```bash
npx wrangler login
npx wrangler d1 create araak-ceo-office
npx wrangler r2 bucket create araak-ceo-office-documents
```

استبدل `database_id` الصفري في `wrangler.jsonc` بالمعرّف الحقيقي الذي أعاده أمر إنشاء D1، أو عيّن `CLOUDFLARE_D1_DATABASE_ID` ثم شغّل `node scripts/configure-cloudflare.mjs`.

أدخل أسرار التشغيل عبر المطالبات المخفية؛ لا تضعها في الكود أو المحادثة:

```bash
npx wrangler secret put SESSION_SECRET
npx wrangler secret put ARAAK_AUTH_USERS
# اختياري، لخدمة التحليل فقط:
npx wrangler secret put GEMINI_API_KEY
npm run deploy:workers
```

- `SESSION_SECRET`: قيمة عشوائية طويلة، 32 حرفًا على الأقل؛ لا تنقل سر الجلسة القديمة حتى لا تصبح الجلسات القديمة صالحة في النسخة الجديدة.
- `ARAAK_AUTH_USERS`: JSON يتضمن حساب مكتب مع دور `ceo` أو `admin` وكلمة مرور فريدة قوية، على نمط المثال المحلي. أسماء الحسابات إيميلات حقيقية بالحروف الصغيرة. لا تحفظ JSON في Git.
- التسجيل الجديد يبقى **قيد الاعتماد** حتى يحدد المكتب نطاق الصلاحيات. اختيار المستخدم لإدارة أثناء التسجيل لا يمنحه صلاحيات تلقائيًا.
- أبقِ الخطط على المجاني عند التجهيز؛ لا تفعّل اشتراكًا مدفوعًا تلقائيًا. تفعيل R2 والفوترة وشروط الدفع مرتبط بحساب Cloudflare. المجاني له حصص وليس سقف تكلفة مضمونًا؛ راقب الاستخدام واضبط التنبيهات. تكلفة الذكاء الاصطناعي والبريد والنطاق مستقلة.
- scrypt وملفات الرفع الكبيرة واستهلاك API يجب اختبارها على الخطة المستهدفة؛ المحاكي لا يثبت المرور ضمن حد CPU الفعلي للخطة المجانية. لا تقلّل قوة تشفير كلمات المرور لتجاوز حد المعالجة.

## الربط مع GitHub

يتضمن المستودع `.github/workflows/cloudflare.yml` للتحقق من كل PR ودفعات `main` وفرع النقل. النشر الحي يدوي من Actions → Cloudflare Workers → Run workflow → deploy، وبعد نجاح التحقق.

أنشئ بيئة GitHub باسم `cloudflare-production`، وضع فيها:

| النوع | الاسم | الغرض |
| --- | --- | --- |
| Secret | `CLOUDFLARE_API_TOKEN` | رمز محدود إلى حساب المشروع، مع صلاحيات Workers Scripts وD1 وR2 وWorkers Assets اللازمة للنشر |
| Secret | `CLOUDFLARE_ACCOUNT_ID` | حساب Cloudflare المالك |
| Variable | `CLOUDFLARE_D1_DATABASE_ID` | معرّف قاعدة D1 التي أنشئت مسبقًا |
| Secret | `SESSION_SECRET` | توقيع جلسات الدخول |
| Secret | `ARAAK_AUTH_USERS` | حسابات المكتب الأولية |
| Secret اختياري | `GEMINI_API_KEY` | التحليل بالذكاء الاصطناعي |
| Variable اختياري | `GEMINI_MODEL` | نموذج التحليل |

لا تمنح تطبيق GitHub الوصول إلى مستودعات لا يحتاجها. يمنع ملف workflow النشر المتزامن، ولا ينشر PRs تلقائيًا. ترفع الأسرار عبر stdin دون طباعتها أو تضمينها في الملفات.

## تحقق الإطلاق ونقل البيانات

1. `/health` يعيد `runtime: cloudflare-workers`.
2. `/ready` و`/api/auth/status` يؤكدان جاهزية الحسابات والتسجيل والتخزين.
3. تسجيل مستخدم حقيقي، واعتماده من المكتب، واختبار دخوله ونطاقه من حسابين مستقلين.
4. إرسال تقرير وتنزيل مرفقه بالحساب المرسل والمكتب، والتحقق من منعه عن حساب آخر حتى لو كان في الإدارة نفسها.
5. إعادة النشر والتأكد من بقاء المستخدمين والتقارير والمرفقات.
6. مراجعة استهلاك CPU خصوصًا تسجيل الحسابات والتحقق من كلمات المرور ورفع الملفات على الخطة المستهدفة.
7. نقل أي بيانات حقيقية من الخادم القديم من نسخة موثوقة فقط، بما فيها ملفات المرفقات والحسابات؛ لا ترفع بيانات `data/executive` المحلية لأنها قد تكون تجارب. لا يوجد استيراد تلقائي أو دمج صامت أو إيقاف للاستضافة القديمة.
8. ربط النطاق الرسمي بعد نجاح التحقق، مع إبقاء النسخة السابقة متاحة للرجوع حتى التأكد من النقل.

النشر الجديد يبدأ بقاعدة فارغة. لا يعد تشغيل `/health` وحده دليلًا على جاهزية التسجيل أو الصلاحيات. للتراجع استخدم إصدار Worker سابقًا متوافقًا مع مخطط القاعدة؛ لا تحذف قاعدة D1 أو حاوية R2 عند التراجع.
